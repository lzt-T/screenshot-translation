## Context

当前所有朗读入口最终调用共享的 `speakText` 和 `playAudioBuffer`，但模型预加载只由口语对话页触发。首页、划词翻译和学习收藏首次朗读时可能同时承担 Worker 创建、模型加载与语音合成开销。

TTS Worker 将模型输出采样直接编码为 WAV，播放器随后立即播放该 WAV。音频数据没有额外的开头静音；当 Windows 声卡或蓝牙输出从休眠状态恢复时，音频时间线开头可能已经推进，导致首个单词或短语听不到。相同文本的第二次播放会复用完整 WAV，且输出设备通常仍处于活跃状态，因此表现正常。

## Goals / Non-Goals

**Goals:**

- 在主进程初始化期间异步预加载一次共享 TTS 模型。
- 在公共 WAV 编码层统一添加固定的短开头静音，覆盖全部朗读入口和缓存播放。
- 复用现有语音服务、Worker、IPC 与播放缓存，不引入新的页面状态或依赖。

**Non-Goals:**

- 不调整音色、语速、句间停顿或 TTS 模型。
- 不重构现有朗读状态管理、取消机制或缓存策略。
- 不为不同页面或音频设备维护不同的缓冲配置。

## Decisions

### 在主进程公共初始化阶段预加载模型

在现有 `init` 流程注册 IPC 后调用 `speechService.preload()`。该方法只创建 Worker 并发送预加载消息，不等待模型完成，因此不会阻塞窗口显示；Worker 内已有 `offlineTtsPromise`，首次朗读与预加载会复用同一初始化任务。

同时移除口语对话页的页面级 `SPEECH_PRELOAD` 调用，因为应用级预加载已经覆盖该场景。保留预加载 IPC 通道以避免无关接口调整，但不再由现有页面主动调用。

备选方案是在每个包含朗读入口的页面分别发送预加载消息。该方案容易遗漏新增入口并产生重复生命周期逻辑，因此不采用。

### 在 WAV 编码层添加 250 毫秒前置静音

公共 WAV 编码器根据采样率预留 250 毫秒的零采样，并将模型采样写入其后。`ArrayBuffer` 初始内容已经为零，只需扩大数据区并调整模型采样的写入偏移，不需要额外遍历或拼接数组。

选择 WAV 编码层而不是页面或播放器层，可以让首次生成和后续缓存播放使用完全相同的音频，并天然覆盖所有调用方。250 毫秒在降低冷启动截断风险与用户可感知延迟之间保持较小折中。

备选方案包括等待媒体 `canplay` 事件或在每个页面播放前延迟。`canplay` 只能说明媒体数据已可解码，不能保证物理输出设备已经唤醒；页面延迟也不会在音频时间线中保留开头内容，因此不采用。

### 保持现有模型停顿参数不变

现有 `silenceScale` 继续用于 TTS 模型内部停顿，不承担输出设备预热职责。前置静音由 WAV 编码器独立处理，避免改变文本内部节奏和语音结果。

## Risks / Trade-offs

- [每次朗读都会增加约 250 毫秒的起播缓冲] → 使用固定且较短的时长，优先保证首音节完整，并避免更复杂的设备检测。
- [应用启动后会提前占用 TTS 模型内存] → 这是缩短所有入口首次朗读等待的必要代价，仍复用单个 Worker 和模型实例。
- [少数设备的唤醒时间可能超过固定缓冲] → 先采用覆盖常见冷启动的最小固定值；如后续仍有设备问题，再基于实际反馈调整该常量。

## Migration Plan

无需数据迁移或接口迁移。发布后由应用启动流程自动预加载模型，现有朗读入口无需适配。若需要回滚，可移除全局预加载调用和 WAV 前置静音偏移，并恢复口语对话页原有的预加载调用。
